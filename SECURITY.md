# Security Policy

OCI Emulator is a local development and learning tool. It is not a cloud, it is not a security boundary, and it must not be exposed to an untrusted network.

This document explains the security model, what is intentionally not protected, and how to report a problem.

---

## 1. Supported versions

| Version        | Supported |
| -------------- | --------- |
| Latest release | Yes       |
| Older releases | No        |

Security fixes are applied to the latest release only. There is no long-term support branch.

---

## 2. Security model

### 2.1 Local only

- The backend binds to `127.0.0.1` by default.
- The Node SSR server binds to `127.0.0.1` and is expected to be reached through the Quarkus proxy.
- There is no TLS.
- There is no authentication for API calls.
- There is no tenant isolation.

If you change the bind address to `0.0.0.0`, you are exposing the emulator to your network. Do not do this on an untrusted network or on a shared host.

### 2.2 Simulated login

The web console login is cosmetic:

- Any non-empty tenancy, user, and password are accepted.
- The password is not stored.
- The `emu_session` cookie is unsigned base64 JSON.
- The cookie only controls which pages the web console shows.
- It does not protect the API.

The API accepts unsigned requests so the OCI CLI and SDKs can work without a browser session. OCI signatures are parsed for tenancy, user, and region, but the signature is not verified.

### 2.3 No secrets

OCI Emulator requires no Oracle Cloud account, API key, or subscription. The local `.oci` key pair generated by `make setup` is a development artifact. It must not be reused anywhere else.

Do not put real credentials, tokens, customer data, or production configuration into the emulator.

### 2.4 Data at rest

- State lives in the local `data/` directory.
- Data is not encrypted.
- Data is not replicated.
- There is no durability guarantee.
- Anyone with filesystem access can read or modify the simulated resources.

### 2.5 Request inspector

The inspector stores the last 500 requests and responses, truncated to 64 KB per body. It can contain resource names, headers, and request payloads. Treat it as sensitive local data:

- Do not paste real credentials into emulator requests.
- Clear the inspector before sharing a screen or exporting data.
- Do not attach inspector output to public issues without redaction.

## 3. What is out of scope

The following are not vulnerabilities in this project because the emulator does not claim to provide these properties:

- Missing authentication or authorization on API endpoints.
- Missing TLS.
- Missing tenant isolation.
- Missing CSRF protection on emulator endpoints.
- Missing rate limiting.
- Missing account lockout.
- Simulated resources exposing simulated data.
- The cosmetic login accepting any credentials.
- OCI signatures not being verified.
- IAM policies not being evaluated.
- Data not being encrypted or durable.
- Denial of service against a local process.
- Local filesystem access by the same user.

The following are in scope:

- A path traversal that escapes the configured data directory.
- Writing files outside the project data and configuration directories.
- Remote code execution through a request payload.
- A proxy rule that forwards API requests to the SSR server, or forwards UI requests to arbitrary hosts.
- An import archive that writes outside the data directory.
- A request inspector that captures more than the documented fields.
- A dependency with a known vulnerability that affects the default runtime.

---

## 4. Safe usage

- Keep `127.0.0.1` as the bind address.
- Do not expose port `4599` or `4600` to a public interface.
- Do not reuse real OCI credentials.
- Use the project-local `.oci` profile.
- Do not store sensitive data in the emulator.
- Stop the emulator before copying or resetting `data/`.
- Review the CLI commands before copying them from the UI.
- Review imported state before running the emulator against it.

---

## 5. Reporting a vulnerability

Do not open a public issue for a security problem.

Send a private report to the maintainer with:

- A description of the issue.
- Steps to reproduce.
- The affected version or commit.
- The impact you believe it has.
- Any suggested fix.

Use the repository security advisory feature if it is available, or contact the maintainer through the address listed in the repository profile.

You can expect:

- An acknowledgment within 7 days.
- A triage decision within 14 days.
- A fix or a documented decision in the next release when the report is in scope.

Please do not publish details before a fix or a decision is available.

---

## 6. Dependency and supply chain

- Dependencies come from Maven Central, npm, and PyPI.
- The backend uses the Quarkus BOM for managed versions.
- The frontend uses pnpm with a committed lockfile.
- The CLI is installed with uv into a project-local virtual environment.
- Do not add dependencies from untrusted sources.
- Do not run the emulator with elevated privileges.

---

## 7. Disclosure policy

- Confirmed issues are fixed in a private branch.
- The fix is released with a note in the release documentation.
- Credit is given to the reporter unless they ask to remain anonymous.
- Out-of-scope reports are answered with a reference to this document.
